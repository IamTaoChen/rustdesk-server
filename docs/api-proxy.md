# Encrypted TCP API proxy

Set `API_PROXY_UPSTREAM=http://127.0.0.1:21114` (or your API origin) to enable the official `HttpProxyRequest` / `HttpProxyResponse` protocol. It is disabled when unset. The upstream must be one HTTP(S) origin without credentials, a path, query or fragment; invalid configuration fails startup. Only clients that completed a supported TCP key exchange can call it. WebSocket and plaintext requests are refused. The API still authenticates every request using its own existing rules; no server login/JWT enforcement is introduced.

Only `/api/` paths and GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS are accepted. Absolute URLs, traversal and encoded path separators are rejected. Upstream redirects are returned to the client, never followed by the server. The proxy ignores ambient HTTP proxy variables and strips hop-by-hop headers, connection-nominated headers and caller-supplied forwarding/source headers. Authorization, API status codes, bodies and end-to-end response headers are preserved. `X-Forwarded-For` and `X-Real-IP` are set to the actual TCP source IP.

Limits: 32 concurrent upstream requests with no queue, three-second connect timeout, ten-second total request/body timeout, 32 KiB request body, 64 request headers / 16 KiB header text, 48 KiB response body and 64 response headers / 8 KiB header text. The inherited signaling frame limit also applies. Failures produce a bounded error response (400/403/405/413/502/503/504); upstream HTTP errors preserve their status and body. Oversized uploads, large address books and recording uploads need the normal HTTP API path.

For correct API audit/rate-limit IPs, configure the API to trust only this server's proxy address and prevent clients from reaching that trusted backend route directly. The API and its trust configuration are managed separately. User-controlled device IDs, UUIDs and authorization headers are never copied into proxy security events. The server key enables encrypted signaling and is not a substitute for API user authentication.
